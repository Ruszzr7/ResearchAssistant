# Research Assistant 稳定性完善实施计划

> 状态：待实施  
> 适用范围：当前单机、单用户版本  
> 目标：在不扩展文章对比和文献检索功能的前提下，把现有功能完善到可稳定长期使用、可重复验收、可打包为 Windows 本地应用的程度。

## 1. 范围与约束

### 1.1 本计划覆盖

- 前端主页面及统一的加载、空状态、错误和重试体验。
- 首页看板及阅读状态统计。
- 文库导入、编辑、筛选、删除和本地文件生命周期。
- 论文助手的解析、理解、对话 API、上下文工程、三个 Skill、证据引用、页面预览与页面操作。
- 研究档案中的对话恢复、证据展示和回到原文。
- API 基础能力测试。
- 自动化端到端回归、真实 API 抽检和 Windows 本地安装/启动验收。

### 1.2 本计划不覆盖

- 文章对比功能。
- 文献检索功能。
- 多用户、登录、注册、权限和云端同步。
- 公网部署、Docker 部署和服务器运维。
- 向量模型、向量数据库或新的 RAG 架构。
- 为现有测试数据编写迁移、兼容或修复逻辑。
- 在 API 设置页增加论文理解专项诊断。
- 全面重写 PDF 阅读器、Agent 架构或前端页面。

### 1.3 数据库原则

- 当前论文、对话和解析产物均为测试数据，可以在需要时清空并重新生成。
- Flyway 仅作为当前数据库结构的唯一来源，用于从空数据库创建当前结构。
- 不为旧测试数据编写字段转换、版本兼容或双写逻辑。
- 需要验证的是“空 MySQL 数据库能否正确初始化并运行”，不是“旧数据库能否升级”。
- 所有初始化验收必须使用独立测试库，不操作日常使用的数据库。

### 1.4 构建原则

- 优先复用当前实现，修复已知断点，不引入新的大框架。
- 实时论文助手和研究档案共用证据展示、定位和跳转逻辑。
- 自动化测试使用独立数据库、独立文件目录和确定性模型桩，不污染用户数据，也不消耗真实 API。
- 真实 API 只用于模型相关链路的阶段验收，不作为普通单元测试依赖。
- 每个阶段独立完成代码、测试和验收，未达到退出标准不得进入下一阶段。

## 2. 完成定义

本计划整体完成需要同时满足：

1. 用户可以从文库导入合法 PDF，并稳定完成解析和论文理解。
2. 用户可以在论文助手中连续提问，回答中的论文事实具有可查看、可跳转、可框选的证据。
3. 刷新页面、切换论文、切换对话或重启应用后，已完成的数据和对话不会丢失。
4. 研究档案可以复现回答、证据和原文位置，而不只是保存回答文本。
5. 无效文件、失败任务、API 不可用等异常都有明确反馈和可执行的恢复入口。
6. 自动化端到端测试可以在不调用真实模型的情况下重复运行。
7. 代表性论文的真实 API 验收通过。
8. Windows 本地安装器能够启动应用，应用只监听本机地址，重启后用户数据仍然存在。

## 3. 测试分层与通用门禁

### 3.1 单元和组件测试

- 后端使用 JUnit 验证业务规则、状态转换、文件生命周期、Agent 协议和异常分支。
- 前端使用 Vitest 验证状态映射、证据视图、页面组件和交互事件。
- 修复缺陷时必须先补充能够复现该缺陷的测试，或者在同一修改中补齐。

### 3.2 确定性端到端测试

端到端测试使用 Playwright、独立测试数据目录和确定性模型桩，覆盖完整业务链路，不访问真实模型 API。

固定样本至少包括：

- 一篇普通单栏短论文；
- 一篇双栏、跨行段落论文；
- 一篇含编号公式论文；
- 一篇含图或表的论文；
- 必要时增加一篇文字层质量较差但仍可解析的论文。

端到端主链路为：

```text
导入 PDF
→ 文件校验
→ 解析完成
→ 理解完成
→ 打开论文
→ 阅读状态更新
→ 创建对话
→ Agent 激活所需 Skill
→ 检索原文证据
→ submit_answer
→ 回答显示引用
→ 点击证据并正确翻页、框选
→ 刷新页面恢复
→ 研究档案恢复回答和证据
→ 从档案回到同一原文位置
```

通用门禁：

- 测试命令可一次启动所需测试环境，不依赖开发者手工准备用户数据。
- Playwright 浏览器依赖有明确安装命令和缺失提示。
- 同一套端到端测试连续执行三次无随机失败。
- 测试完成后不在用户文库、数据库或正式存储目录残留数据。

### 3.3 真实 API 验收

真实 API 验收只在以下情况下执行：

- 修改论文解析或论文理解输入链路；
- 修改上下文工程、Agent、Skill、证据检索、引用或页面操作；
- 发布新的本地安装包之前。

真实 API 结果允许模型措辞不同，但工具调用、证据约束、终止状态和页面定位必须满足确定性标准。

### 3.4 每阶段通用回归命令

至少执行：

```text
后端：cd backend && mvnw.cmd test
前端单测：cd frontend && npm.cmd run test:unit
前端构建：cd frontend && npm.cmd run build
端到端：cd frontend && npm.cmd run test:e2e
```

如果某阶段尚未具备端到端运行条件，必须在阶段报告中明确阻塞原因，不能以单元测试代替端到端验收。

## 阶段 0：建立稳定验收基线

### 目标

先建立能够复现核心业务链路的测试基线，后续所有修改都由同一套验收保护，避免再次出现单元测试通过但真实页面引用或框选失效的情况。

### 实施内容

1. 整理固定 PDF 测试样本，并记录每篇样本要验证的结构特征。
2. 为测试环境配置独立数据库和独立存储目录。
3. 增加确定性模型实现或测试适配层，使其能够按预设轨迹完成：
   - 加载论文画像；
   - 生成合法 Need；
   - 调用证据工具；
   - 根据工具结果调用 `submit_answer`；
   - 必要时发起页面操作。
4. 将现有 Playwright 冒烟测试扩展为至少一条完整论文问答链路。
5. 增加浏览器依赖安装说明，并确保测试失败时保留截图、控制台错误和轨迹文件。
6. 建立阶段验收记录模板，至少记录：提交版本、测试数据、测试命令、结果、真实 API 调用情况和遗留问题。

### 自动化测试

- 合法 PDF 可以导入并进入解析任务。
- 解析和理解任务可以由测试实现稳定进入完成态。
- 可以创建对话、提交问题并得到带证据回答。
- 点击证据可以跳页并出现至少一个有效框选。
- 刷新页面后回答和引用仍然存在。
- 测试失败时 Playwright 能输出可定位的失败信息。

### 人工验收

- 在可见浏览器中运行一次完整链路，确认不是只验证接口返回值。
- 检查正文段落、跨行文本和公式编号至少各一个跳转结果。
- 检查测试运行前后用户正式数据库和论文目录没有变化。

### 退出标准

- 完整端到端链路连续运行三次通过。
- 后端测试、前端单测和构建通过。
- 后续阶段能够直接复用测试环境和固定样本。

## 阶段 1：阅读状态、看板和基础页面状态

### 目标

统一未读、正读、已读的业务语义，使看板、文库和论文阅读页显示一致；同时补齐主要页面的错误反馈和重试入口。

### 阅读状态规则

- `UNREAD / 未读`：论文尚未成功打开 PDF。
- `READING / 正读`：用户第一次成功打开 PDF 后自动进入。
- `READ / 已读`：仅由用户明确执行“标记为已读”进入。
- 已读论文再次打开时保持已读，不自动退回正读。
- 翻到最后一页不自动标记已读。
- 用户可以在文库中手动切换三种状态。

### 实施内容

1. 在 PDF 真正加载成功后更新阅读进度；如果当前状态为未读，同时切换为正读。
2. 保证首次打开停留在第一页时也会触发状态更新，不能依赖翻页事件。
3. 增加清晰的“标记为已读”入口，并复用现有论文更新接口或增加最小专用接口。
4. 将“已读 10 分钟”等阅读时长文案改为“阅读时长 10 分钟”。
5. 看板直接按统一状态统计，并增加“未分类论文”数量。
6. 看板任务状态区分：
   - 当前仍失败、尚未被成功重试覆盖的任务；
   - 仅作为历史记录存在的旧失败任务。
7. 为看板、文库、论文页和研究档案补充可见的加载失败状态与重试按钮；保留必要的空状态，不增加装饰性组件。
8. 当前测试数据允许统一重置阅读状态，不编写旧状态兼容逻辑。

### 单元和组件测试

- 未读论文首次成功打开后变为正读。
- PDF 加载失败时仍保持未读。
- 已读论文再次打开后仍为已读。
- 翻到最后一页不会自动变为已读。
- 用户手动切换状态后看板统计同步变化。
- 阅读时长累计不会修改已读/正读语义。
- 未分类论文进入看板统计。
- 页面接口失败时显示错误和重试入口，重试成功后恢复正常内容。

### 端到端测试

1. 导入新论文并确认看板未读数量增加。
2. 成功打开论文并确认状态变为正读。
3. 刷新和重新进入后确认状态仍为正读、页码和时长仍在。
4. 点击“标记为已读”，确认文库和看板同时更新。
5. 再次打开论文，确认状态不降级。

### 人工验收

- 看板、文库卡片/表格、论文详情显示的状态一致。
- “阅读时长”和“阅读完成状态”不会再使用相同文案造成误解。
- 当前失败任务不会被已经成功完成的历史重试错误污染。

### 退出标准

- 三种状态的全部转换测试通过。
- 看板数量与对应文库筛选结果逐项一致。
- 主要页面不存在接口失败后无提示的空白状态。

## 阶段 2：研究档案证据复现

### 目标

使研究档案成为可追溯记录：历史回答不仅能阅读，还能查看当时使用的证据，并回到正确论文页面和定位框。

### 实施内容

1. 研究档案读取并展示消息中已经保存的 `evidence`、`claims` 和回答块关系。
2. 复用论文助手现有的证据视图映射、完整文本展示和公式可靠性规则，不实现第二套转换逻辑。
3. 历史回答中的引用使用与实时回答相同的编号、去重和展开方式。
4. 点击证据时携带论文 ID、页码和全部 locator，进入论文页后完成翻页和框选。
5. 处理以下边界：
   - 当前正在查看另一篇论文；
   - 证据具有多个矩形；
   - 证据跨行或跨栏；
   - 公式只有编号定位；
   - 旧消息确实没有完整定位信息。
6. 没有可靠定位的旧消息只显示保存时已有内容，不伪造框选。
7. 会话列表改为分页加载；接口返回总数和当前页，前端可继续查看旧会话。
8. 只显示每轮最终状态和必要的中文错误原因，不向普通用户展开内部 ToolCall 日志。

### 单元和组件测试

- 保存的 evidence 可以映射为与实时回答一致的视图模型。
- 相同物理证据不会在历史回答中重复显示。
- 多 locator 不会只保留第一个矩形。
- 从档案生成的跳转参数包含正确论文 ID 和页码。
- 缺少定位信息时不显示虚假的可跳转按钮。
- 分页切换、空档案和加载失败状态正常。

### 端到端测试

1. 在论文助手完成一轮带正文证据的回答。
2. 进入研究档案，确认回答、引用和完整证据仍然存在。
3. 点击证据，确认进入正确论文、正确页面并显示完整框选。
4. 对公式编号证据重复上述操作。
5. 创建超过单页容量的会话数据，确认较早会话仍可访问。

### 人工验收

- 随机选择至少三条历史回答，与实时回答逐项比较引用编号、证据内容和定位效果。
- 从档案进入论文后返回档案，档案列表位置和选择状态合理保留。

### 退出标准

- 新产生的带证据回答可以在档案中完整复现。
- 正文和公式证据均可以正确跳转。
- 实时页面和档案页面不再存在两套不同的证据语义。

## 阶段 3：文库文件与数据一致性

### 目标

确保导入、覆盖和删除失败时，数据库记录与本地文件不会出现一边成功、一边失败的状态。

### 实施内容

1. 上传文件先写入正式存储目录内的临时位置。
2. 使用 PDFBox 实际打开文件并读取页数，不再只依赖 `.pdf` 扩展名。
3. 对损坏、空文件、加密且无法打开、伪装扩展名的文件返回明确中文错误。
4. 校验通过后使用唯一正式文件名移动文件并写入数据库。
5. 新建论文时：数据库事务回滚必须清理本次新增文件。
6. 覆盖论文时：
   - 新文件使用新路径，不原地覆盖旧文件；
   - 数据库提交成功后删除旧文件；
   - 数据库回滚时删除新文件并保留旧文件。
7. 删除论文时，在数据库提交成功后清理 PDF、对应图像制品和明确归属该论文的文件。
8. 删除研究会话或清理暂存附件时，同步清理 Agent 附件物理文件，避免长期积累孤儿文件。
9. 收紧论文写入参数：
   - 阅读状态和来源方式只接受合法值；
   - 当前页、总页数和阅读时长不由普通论文编辑请求任意覆盖；
   - 文件夹和标签引用必须存在。
10. 暂不为查重引入新表或新索引；只有真实数据量证明现有文件哈希扫描造成明显等待时再优化。

### 单元和集成测试

- 正常 PDF 上传成功并得到正确页数。
- 非 PDF、损坏 PDF、空文件和不可打开的加密 PDF 被拒绝。
- 文件校验失败时没有论文记录和残留正式文件。
- 数据库写入失败时新增文件被清理。
- 覆盖失败时旧论文和旧 PDF 仍然可用。
- 覆盖成功后新文件可用，旧文件被清理。
- 删除论文后相关文件被清理，路径越界保护仍有效。
- 删除会话后其物理附件被清理，其他会话附件不受影响。
- 非法阅读状态、页码和不存在的文件夹/标签被拒绝。

### 空数据库初始化验收

1. 创建独立的空 MySQL 测试库。
2. 使用当前配置启动后端并由 Flyway 创建当前结构。
3. 完成论文导入、读取、更新、删除和会话创建的最小操作。
4. 验收完成后删除该独立测试库。

该验收不导入或转换任何旧数据。

### 端到端测试

- 浏览器上传合法 PDF 后能够进入文库并打开。
- 上传非法 PDF 时显示明确错误，刷新后没有幽灵记录。
- 覆盖操作失败时原论文仍可打开。
- 删除论文后文库、看板和本地文件状态一致。

### 退出标准

- 文件与数据库异常分支测试全部通过。
- 空 MySQL 数据库能够初始化并完成最小业务操作。
- 不存在由本阶段测试产生的孤立 PDF、图像或附件。

## 阶段 4：论文助手和三个 Skill 的稳定性闭环

### 目标

不重构现有基础架构，通过补齐运行控制、Skill 契约和真实链路回归，使解析、理解、对话、证据和页面操作稳定协作。

### 4.1 解析与理解

1. 保持当前 PDFBox 版面事实、重要区域视觉恢复和整篇理解链路。
2. 固定解析版本、PDF 哈希和理解产物之间的一致性检查。
3. 解析失败时允许明确重试；理解失败不通过无限延长超时掩盖根因。
4. 当前测试论文可以删除旧产物并重新解析、理解，不增加兼容读取。
5. 继续保持论文理解关闭不必要的深度思考配置。

### 4.2 对话 API 与上下文

1. 保持 Turn、Run、ToolCall 和研究消息的现有单写职责。
2. 验证同论文多对话之间消息、摘要、选区和证据上下文完全隔离。
3. 验证刷新、离开页面和重新进入后，运行结果由服务端恢复。
4. 增加明确的“取消回答”：
   - 排队中或运行中的 Run 可以进入 `CANCELLED`；
   - 尽可能中断供应商请求；
   - 供应商无法中断时，迟到结果不得覆盖取消状态；
   - 前端停止观察与服务端取消保持不同语义。
5. 保持上下文压缩和 Skill 激活 transcript 的现有设计，除真实失败样本外不增加规则。

### 4.3 三个 Skill

#### 论文画像 Skill

- 画像只提供全文方向和候选来源，不能直接作为引用。
- 画像已在当前上下文中时不重复读取。
- 精确事实和否定性判断必须进入证据 Skill。

#### 证据 Skill

- Need 必须满足现有锚点契约，并优先在一次调用中覆盖全部独立事实需求。
- 后续只重试未解决 Need，保持原 ID 和 objective。
- 相同请求、相同来源和停止态不得继续重复检索。
- Agent 必须阅读证据后决定使用或放弃，工具不调用第二个模型代替判断。
- 只引用实际使用的来源；同一物理证据不重复展示。
- 文本证据保留完整内容和全部 locator。
- 公式文本不可靠时只把可靠编号或视觉内容交给 Agent，不将内部诊断文案写入回答。

#### 页面操作 Skill

- 只在用户明确请求跳转、高亮、下划线、笔记或评论时激活。
- 没有可信 `sourceObjectId` 时先通过证据 Skill 获取来源。
- 一次工具调用只执行一个明确操作。
- 必须等待客户端真实回执后才能声称操作成功。
- ActionTicket 过期时允许重新签发；目标仍有实质歧义时先澄清。
- 不向模型开放坐标，也不建立新的页面操作工作流。

### 单元和集成测试

- 解析产物、画像和来源目录绑定同一 PDF 哈希及解析版本。
- Agent 对论文事实回答必须通过 `submit_answer` 终止。
- 未调用 `submit_answer` 的普通文本不能保存为合法事实回答。
- Need 输入、补检索、重复请求、无进展和停止协议均有测试。
- 同一证据不会因文本来源和视觉恢复来源同时存在而重复。
- `contentComplete=true` 的正文返回完整内容和全部 locator。
- 取消 Run 后迟到模型结果不会形成助手消息。
- 两个对话的上下文和附件完全隔离。
- 页面操作成功、失败、重复回执和票据过期均有测试。

### 确定性端到端测试

- 普通概括问题能够先使用画像，再检索必要证据并提交回答。
- 精确公式问题能够找到正确公式编号，必要时获取视觉内容。
- 跨轮追问只补检索缺少的 Need，不重复读取已充分来源。
- 点击正文、跨行、双栏和公式证据后定位正确。
- 刷新页面后回答、引用和未完成运行能够正确恢复。
- 用户取消回答后界面停止等待，刷新后仍显示取消终态。
- 页面操作必须在客户端回执后显示成功。

### 真实 API 验收

选择代表性测试论文，每篇至少询问：

> 论文的核心创新点是什么？

对于含重要公式的论文，再询问：

> 文章最核心的观点或公式是什么？

逐篇统计：

- 是否正常完成或出现超时、截断、协议错误；
- 是否激活了合适的 Skill；
- Need 是否具体、中立且包含可用锚点；
- 是否出现完全相同的重复调用；
- 是否使用了实际检索到的证据；
- 是否通过 `submit_answer` 完成；
- 引用是否与回答块对应；
- 是否存在重复证据、断裂证据或错误公式证据；
- 点击后页码和框选是否正确。

真实 API 回答质量由人工结合 PDF 复核，不以模型措辞完全一致作为验收要求。

### 退出标准

- 所有确定性端到端场景通过。
- 真实 API 样本不存在系统性无证据回答、重复检索、错误终止或定位失效。
- 个别论文证据不足时，Agent 能明确限制并停止，而不是编造内容或无限检索。
- 三个 Skill 的职责边界没有被运行时代码重新写成僵硬的内容规则集合。

## 阶段 5：API 基础能力测试完善

### 目标

设置页只判断用户接入的模型 API 是否满足项目的基本通信和工具协议，不执行论文理解业务。

### 实施内容

1. 保留并统一验证：
   - 普通文字输入与输出；
   - 图片输入；
   - 结构化输出；
   - 工具调用；
   - 工具结果返回后的继续回答。
2. 原生 PDF 输入仅作为可选能力展示，不作为项目可用的必要条件。
3. 显示能力验证时间、有效状态和必要的重新测试入口。
4. 将失败分类为可操作的中文提示：
   - 地址或网络不可达；
   - API Key 无效；
   - 模型不存在或无权限；
   - 图片不支持；
   - 工具调用不支持；
   - 结构化输出不支持；
   - 请求超时或供应商协议不兼容。
5. 测试使用极小的固定文字和图片，不读取论文、不创建任务、不修改文库。
6. 翻译服务状态与对话/理解模型能力分开显示，不混成一个测试结论。

### 单元和集成测试

- 全能力支持时返回完整成功结果。
- 缺少图片、工具或结构化输出时准确指出具体能力。
- 鉴权、模型不存在和超时能够得到不同提示。
- 能力测试不会保存草稿中的错误配置。
- 能力测试不会创建论文、解析任务、研究会话或消息。

### 人工验收

- 使用当前真实 API 配置完成一次能力测试。
- 使用一组故意错误的 Key 或模型名确认提示明确。
- 确认测试期间文库和任务中心没有新增业务记录。

### 退出标准

- 用户能够仅根据设置页结果判断 API 是否满足论文助手运行的基础要求。
- API 测试不承担论文解析或论文理解质量验收。

## 阶段 6：Windows 本地应用打包

### 目标

在核心功能稳定后，把项目整理为无需 Docker、无需 Node 开发环境、只供本机单用户使用的 Windows 应用。

### 实施内容

1. 将 Vue 生产构建产物交由 Spring Boot 提供，运行时不再单独启动 Vite。
2. 使用 Java `jpackage` 或等价的轻量安装工具生成 Windows 安装器和启动入口。
3. 安装包捆绑所需 Java 运行环境，不要求用户预装 JDK。
4. 第一版本继续使用本机 MySQL：
   - 启动时检查 MySQL 是否可连接；
   - 不可用时显示明确中文说明；
   - 不在本阶段替换数据库或自动安装数据库服务。
5. 服务仅监听 `127.0.0.1`，启动成功后自动打开默认浏览器。
6. 启动器负责：
   - 防止重复启动；
   - 检查端口占用；
   - 等待后端健康检查；
   - 打开页面；
   - 提供安全停止入口；
   - 写入可定位的本地日志。
7. 用户数据、配置和日志放在明确的本地用户目录，应用升级不覆盖用户数据。
8. 卸载时默认保留论文和数据库；如需删除数据，必须单独明确选择。
9. 提供简单备份和恢复脚本：
   - 备份 MySQL 数据；
   - 备份 PDF、图像和 Agent 附件目录；
   - 生成包含版本和时间的清单；
   - 恢复前检查目标目录和数据库，避免覆盖错误位置。

### 自动化测试

- 前端静态资源能够通过 Spring Boot 正常访问。
- 未启动后端时启动器可以启动；已经启动时不会创建第二个实例。
- 端口被未知进程占用时停止并提示，不强制结束该进程。
- MySQL 不可用时给出可操作错误，不进入假启动成功状态。
- 健康检查通过前不提前打开不可用页面。

### 安装验收

在干净的 Windows 测试环境中验证：

1. 安装器能够完成安装并创建启动入口。
2. 机器无需安装 Node.js 或 JDK。
3. 已满足 MySQL 前置条件时，一次启动可以打开应用。
4. 导入论文、解析、理解和问答主链路正常。
5. 关闭并重新启动后论文、阅读进度、对话和证据仍然存在。
6. 重启 Windows 后应用仍可正常启动。
7. 卸载应用后用户数据按默认策略保留。
8. 备份结果能够在独立测试环境恢复并打开论文及研究档案。

### 退出标准

- 安装、启动、停止、重启、卸载和恢复验收全部通过。
- 应用不依赖 Docker、Node 开发服务器或用户预装 JDK。
- 本地端口不向局域网暴露。
- 安装器失败不会破坏已有用户数据。

## 4. 最终综合验收

全部阶段完成后执行一次完整发布候选验收。

### 4.1 功能矩阵

| 范围 | 必须通过的行为 |
|---|---|
| 看板 | 统计准确、未分类可见、当前错误可处理 |
| 文库 | 合法导入、非法拒绝、筛选编辑、覆盖删除一致 |
| 阅读 | 未读→正读自动、已读手动、页码与时长恢复 |
| 解析 | 固定单栏、双栏、公式、图表样本产物有效 |
| 理解 | 代表性论文画像可用，失败可重试且原因可见 |
| 对话 | 连续问答、上下文隔离、取消和刷新恢复正常 |
| Skill | 画像定向、证据支撑、页面操作职责清楚 |
| 证据 | 内容完整、不重复、引用对应、定位正确 |
| 预览操作 | 正文/公式跳转、框选、标注和回执正常 |
| 研究档案 | 回答、证据、状态和回到原文完整复现 |
| API 设置 | 文字、图片、结构化和工具能力判断准确 |
| 本地应用 | 安装、启动、重启、数据保留和恢复正常 |

### 4.2 稳定性门槛

- 后端全量测试零失败、零错误。
- 前端全量单测和生产构建通过。
- 确定性端到端套件连续三次通过。
- 固定真实 API 样本完成验收，并保存逐篇结果。
- 空 MySQL 测试库初始化和最小业务操作通过。
- Windows 安装、重启和恢复测试通过。
- 浏览器控制台没有影响主流程的未处理异常。
- 所有失败路径都有中文提示，且不会留下错误完成状态或孤立文件。

### 4.3 发布阻断条件

出现以下任一情况，不得进入下一阶段或生成稳定安装包：

- 合法 PDF 导入后数据库与文件状态不一致；
- 论文事实回答没有实际证据却被保存为正常完成；
- 证据点击无法回到正确页面，或框选指向错误内容；
- 刷新、切换页面或重启导致已完成回答丢失；
- 研究档案无法复现新产生回答的证据；
- API 能力测试显示成功，但缺少项目必需的图片或工具调用能力；
- 安装、升级或卸载可能静默删除用户数据；
- 自动化测试依赖用户正式数据库或真实 API 才能运行。
